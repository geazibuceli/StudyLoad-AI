# Data Card: StudyBalance AI Synthetic Workload Dataset

## Dataset summary

| Item            | Value                                                           |
| --------------- | --------------------------------------------------------------- |
| Dataset name    | StudyBalance AI synthetic workload dataset                      |
| Dataset version | `1.0.0` as embedded in model artifact `1.0.0`                   |
| Generator       | `scripts/synthetic-data.js`                                     |
| Default seed    | `42`                                                            |
| Records         | 3,600                                                           |
| Features        | 12 numerical academic workload features                         |
| Labels          | `low`, `moderate`, `high`                                       |
| Class balance   | 1,200 records per class by construction                         |
| Personal data   | None                                                            |
| Missing values  | None by construction                                            |
| Storage         | Generated in memory; summarized in the versioned model artifact |
| License         | MIT                                                             |

## Purpose

The dataset exists to support development, testing, and demonstration of a complete machine-learning pipeline without collecting student records. It provides deterministic feature rows for training a multinomial logistic regression model.

It is not a survey, observational cohort, clinical dataset, educational record system export, or representative sample of university students.

## Relationship to user data

The synthetic dataset and planner data are separate:

- synthetic records are generated by source code with a fixed seed;
- planner tasks remain in browser `localStorage` by default;
- an analysis request is processed in server memory;
- user-entered tasks are never silently added to training;
- the model artifact contains coefficients and aggregate training metadata, not task titles or student records.

## Unit of observation

One record is an artificial academic workload **feature vector** representing a hypothetical planner snapshot. It is not a simulated person and contains no stable identity, text, course name, institution, or longitudinal history.

The generator creates features directly. It does not first create a complete set of tasks and pass that set through the application's production feature extractor. This distinction is a major limitation because generated feature combinations can differ structurally from real schedule-derived combinations.

## Feature schema

| Feature                 | Synthetic generation                                                                                       |
| ----------------------- | ---------------------------------------------------------------------------------------------------------- |
| `pendingTaskCount`      | Integer from 0 through 20                                                                                  |
| `overdueTaskCount`      | Binomial draw bounded by pending tasks, using a sampled probability from 0 up to, but not including, 0.30  |
| `dueWithin7DaysCount`   | Binomial draw over non-overdue tasks, using a sampled probability from 0.08 up to, but not including, 0.72 |
| `examWithin14DaysCount` | Binomial draw over non-overdue tasks, using a sampled probability from 0.02 up to, but not including, 0.28 |
| `remainingHours`        | Pending task count multiplied by sampled effort and adjusted by average progress                           |
| `dueWithin7DaysHours`   | Bounded by remaining hours and scaled by near-term task count                                              |
| `weeklyAvailableHours`  | Continuous draw from 6 up to, but not including, 46 hours                                                  |
| `loadRatio`             | Constructed near-term, overdue, and paced future hours divided by availability                             |
| `deadlineCluster3Days`  | Integer bounded by pending, near-term, and overdue task counts                                             |
| `highPriorityTaskCount` | Binomial draw over pending tasks, using a sampled probability from 0.10 up to, but not including, 0.58     |
| `nearestDeadlineDays`   | 0 when overdue work exists; otherwise 0 through 6 for near-term work or 7 through 30                       |
| `averageProgress`       | Continuous draw from 0 up to, but not including, 88 percent when work is pending                           |

When `pendingTaskCount` is zero, dependent workload features are zero, `nearestDeadlineDays` is 30, and `averageProgress` is 100.

The exact generator implementation is authoritative. Rounded prose ranges in this card are provided for review, not as an alternative executable specification.

## Label construction

The generator computes a latent score:

$$
\begin{aligned}
s ={}& 26\,\mathrm{clip}(\text{loadRatio}, 0, 2.5) \\
&+ 4.8\,\text{overdueTaskCount} \\
&+ 2.2\,\text{dueWithin7DaysCount} \\
&+ 3.2\,\text{examWithin14DaysCount} \\
&+ 3\,\max(0, \text{deadlineCluster3Days} - 1) \\
&+ 1.4\,\text{highPriorityTaskCount} \\
&+ 0.06\,\text{remainingHours} \\
&- 0.11\,\text{averageProgress} \\
&- 0.3\,\min(\text{nearestDeadlineDays}, 14) \\
&+ 4.5\,\epsilon
\end{aligned}
$$

where \(\epsilon\) is a standard Gaussian value produced by the deterministic seeded pseudorandom stream.

Labels are assigned as follows:

| Label      | Latent score rule                    |
| ---------- | ------------------------------------ |
| `low`      | Below 20                             |
| `moderate` | From 20 up to, but not including, 52 |
| `high`     | 52 or higher                         |

The score and thresholds are project assumptions created for demonstration. They are not derived from a validated questionnaire, student outcome, health measure, or expert annotation.

## Sampling and balancing

The generator uses a seeded Mulberry32-style pseudorandom function and Box-Muller Gaussian noise. It proposes records sequentially and accepts them only while the proposed label's quota remains open. Generation stops when each class contains 1,200 records.

This rejection process creates exact class balance but changes the natural frequency and conditional distribution of accepted examples. The 1:1:1 balance must not be interpreted as the prevalence of workload levels in any student population.

## Training and validation split

The 3,600 accepted records are shuffled with a second deterministic stream initialized with seed `43`. The first 80 percent form the training split and the remaining 20 percent form the synthetic validation split.

| Split              | Records |   Low | Moderate |  High |
| ------------------ | ------: | ----: | -------: | ----: |
| Full generated set |   3,600 | 1,200 |    1,200 | 1,200 |
| Training           |   2,880 |   966 |      966 |   948 |
| Validation         |     720 |   234 |      234 |   252 |

Validation class counts are obtained from the row totals of the committed confusion matrix; training counts are the corresponding remainder from the balanced full set. Normalization means and population standard deviations are calculated from the training split only.

The split is suitable for deterministic pipeline diagnostics. It is not institution-external, time-separated, person-separated, or independent of the generation and labeling design.

## Processing

The training pipeline:

1. maps each record into the fixed schema order;
2. shuffles and splits records deterministically;
3. calculates z-score parameters from training vectors;
4. standardizes both partitions with training parameters;
5. trains the softmax model with full-batch gradient descent;
6. reports accuracy, macro F1, and a synthetic validation confusion matrix;
7. serializes coefficients, scaler values, settings, labels, metrics, and limitations into the artifact.

No imputation, augmentation, human labeling, scraping, or third-party data source is involved.

## Privacy and sensitivity

The generated records represent no person and contain no personal data. This makes the dataset appropriate for software testing without exposing student records.

Synthetic data do not make the overall application risk-free. Real task titles and schedules can reveal routines or academic difficulties when entered into the planner. Their handling is documented separately in [Privacy and Ethics](docs/PRIVACY_AND_ETHICS.md).

## Known limitations

### No population representation

The generator encodes hand-selected ranges and relationships. It has no institution, country, program, academic level, calendar system, accessibility context, employment pattern, caregiving responsibility, or socioeconomic variation.

### Constructed-label circularity

The target is calculated from the feature families used to train the model. Validation primarily measures how well the model approximates the synthetic scoring function.

### Feature inconsistency risk

Because features are generated directly, a row may combine values that a real task schedule and production feature extractor would not produce together. No formal constraint or distribution-distance analysis is currently reported.

### Coverage mismatch

The HTTP API permits baseline weekly availability from 1 through 168 hours, while synthetic availability covers only about 6 through 46 hours. Real task counts, effort values, deadline patterns, and progress distributions may also fall outside synthetic support.

### Artificial balance

Class quotas remove any information about real prevalence. Accuracy on the balanced holdout can be misleading under a different deployment distribution.

### No longitudinal structure

Records are independent snapshots. The dataset cannot evaluate change over semesters, repeated use by one student, concept drift, alert fatigue, or delayed effects of recommendations.

### No fairness evidence

There are no demographic attributes or real groups on which to measure disparities. Their absence prevents subgroup evaluation and does not prove fairness.

## Appropriate uses

- Unit and integration tests for feature-to-model behavior.
- Reproducibility checks for the trainer and artifact.
- Educational explanation of synthetic data and softmax classification.
- Early interface and API development where real records are unnecessary.
- A clearly labeled software baseline before responsible data collection.

## Inappropriate uses

- Claims about real student prevalence, accuracy, calibration, fairness, or well-being.
- Clinical, psychological, academic-success, or dropout prediction.
- Training a production decision system without independent validation.
- Re-identification or simulation of a particular person.
- Replacing participatory research, ethics review, or informed consent.
- Presenting synthetic metrics as evidence that an intervention works.

## Reproducibility

Check the committed model artifact against a fresh deterministic build:

```bash
node scripts/train-model.js --check
```

Generate the dataset and rewrite the artifact through the training script:

```bash
node scripts/train-model.js
```

The dataset is generated in memory rather than committed as a separate table. The source, seed, sample count, label rule, split logic, and training settings are version-controlled.

## Maintenance and change policy

A change to any generator range, correlation, score coefficient, threshold, noise scale, quota, seed, feature definition, or split procedure creates a materially different dataset version. Such a change must:

- update the artifact version and metadata;
- update deterministic snapshots and tests;
- regenerate all reported synthetic metrics;
- update this card and [MODEL_CARD.md](MODEL_CARD.md);
- explain why the new assumption is preferable;
- avoid describing a metric increase as real-world improvement.

The next meaningful data milestone is not a more elaborate synthetic generator. It is a responsibly designed, ethically reviewed validation study with an explicit non-clinical target, appropriate consent, representative sampling goals, and a plan for privacy, withdrawal, deletion, subgroup analysis, and harm monitoring.
